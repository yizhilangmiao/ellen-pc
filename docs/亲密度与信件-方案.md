## 1. 亲密度模型

### 1.1 为什么换

现在阶段靠评估模型给分：同两句话，模型心情不同可能给 0.25 也可能给 1.5，用户不知道自己要聊多久才升级。改成点数制后：**聊够多少条、认识够几天 = 什么阶段**，能算给人看。

三轴不删，降级为「表达参考」：
- 继续由模型打分，用于心情、「有待修复」（`trust` 或 `closeness` ≤ -10 仍然直接掉档）
- 不再决定阶段

### 1.2 点数公式

```
point += 1        每一条用户消息
point += 3        每个「聊过天的日子」第一次出现
```

- 只统计 `source_events` 里 `role = 'user'` 的行（语音转写也算，附件/贴纸不算）
- 活跃日 = `count(distinct date(occurred_at))`，一天只加一次
- 不设日上限（可选接口：`dailyPointCap`，默认关）

### 1.3 阶段门槛（默认值，角色包可覆盖）

| 阶段 | key | 点数 | 天天聊 10 条大概 |
| --- | --- | --- | --- |
| 陌生 | `learning` | 0 | — |
| 相识 | `acquainted` | 30 | 2~3 天 |
| 熟悉 | `familiar` | 100 | 8 天 |
| 信赖 | `trusted` | 250 | 19 天 |
| 亲近 | `close` | 450 | 35 天 |
| 恋人 | `lover` | 700 | 54 天 |

- 恋人档仍要 `romance === true`（角色包 `relationship.allowRomance`）
- 逐级判定，`strained`（有待修复）优先
- 门槛写进 `POLICY.stageGates`，角色包用 `relationship.stageGates` 覆盖（已支持）

### 1.4 历史记录回填

首次启用新算法时跑一次：

```sql
SELECT count(*) FILTER (WHERE role='user'),          -- 消息条数
       count(DISTINCT substr(occurred_at,1,10)),     -- 活跃天数
       min(occurred_at)                              -- 认识起点
FROM source_events
```

- 算出 `points = 条数 × 1 + 活跃天数 × 3`，写进 `relationship_state.intimacy_baseline`
- 之后 `亲密度 = baseline + 新增长`，历史不清零
- 界面上显示「已按历史 1,240 条 / 87 天折算」
- 回填只做一次，留 `backfilled_at` 标记

### 1.5 对外接口

```js
// memory/src/intimacy.cjs（新建）
computePoints({ messages, activeDays })       // → number
resolveStage({ points, romance, strained })   // → { key, label, next, progress }
explain({ messages, activeDays, points })     // → 「还差 12 条 / 3 天到熟悉」
```

`relationship-store` 加：`intimacy()` 返回 `{points, level, stage, progress, breakdown}`，聊天界面和 `dialogue-guidance` 都从这里取。

## 2. 信件系统

### 2.1 什么时候写

| 触发 | 内容 |
| --- | --- |
| 相识 / 熟悉 / 信赖 / 亲近 | 一封普通信，150~300 字 |
| 恋人 | 一封**正式情书**，400~600 字，带称呼与落款 |
| 降级到「有待修复」 | 不写信（避免惩罚性内容），只记一条事件 |

- 检测点：每轮回复完成后比对 `prevStage → newStage`，升了才写
- 生成异步，不阻塞回复；失败标记 `pending`，下次启动补写
- 同一阶段只写一封（`character_id + stage_key` 唯一）

### 2.2 怎么写

新建 `src\letter-compose.cjs`：

- 输入：角色人格（`persona.base/knowledge`）、阶段名与阶段行为说明（`STAGES`）、这段时间的真实记忆（`selectCharacterContext` 取 3~5 条相关记忆）、统计事实（认识多少天、聊过多少条、最近聊了什么）
- 输出：`{ title, body }`
- 硬规则写进 prompt：**只写这段时间真实发生过的事**；不编造没记录的经历；信里不出现数值和阶段术语；恋人档允许更郑重、更长

### 2.3 存哪

新表，加在 `memory\src\relationship-schema.sql`（同一个 DB，同一身份校验）：

```sql
CREATE TABLE IF NOT EXISTS letters (
  id TEXT PRIMARY KEY,
  character_id TEXT NOT NULL,
  stage_key TEXT NOT NULL,
  kind TEXT NOT NULL CHECK(kind IN ('stage','love_letter')),
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  created_at TEXT NOT NULL,
  read_at TEXT,
  UNIQUE(character_id, stage_key)
) STRICT;
```

- 只增不改（跟 `relationship_events` 一样加 immutable trigger），避免信被后来的自己改写
- 导出：`letters\` 目录下存一份 `.md` 副本，方便备份/带走

### 2.4 怎么看

- 入口：聊天界面右上角一个「信」按钮，带未读数角标
- 面板：复用 `journal-panel.js` 的 dialog 结构，列表按时间倒序（阶段名 + 日期 + 标题）
- 详情：信纸样式；情书单独一套（居中、落款）
- 未读：打开即标记 `read_at`；可反复看，不删

## 4. 要你拍板的 5 件事

1. **点数权重**：每条消息 +1、每个活跃日 +3，行不行？还是想让「天数」更重（+5）或更轻（+1）？
2. **门槛快慢**：上表「天天聊到恋人约 54 天」是快还是慢？整体乘 0.7（更快）或 1.5（更慢）一句话就能调。
3. **历史回填要不要补信**：老记录折算后可能一次跨 3 个阶段。补 3 封，还是只写当前最高那一封？（我建议只写最高那封 + 面板标注「更早的阶段已走过」）
4. **信的生成模型**：跟聊天同一个模型，还是指定一个更擅长写信的？
5. **情书的私密性**：要不要加锁（打开要确认），还是跟其它面板一样直接开？

## 5. 分期

**第一期（能跑能看）**
点数制 + 阶段判定 + 历史回填 + 普通信生成 + `letters` 表 + 面板列表/详情 + 未读标记

**第二期（打磨）**
恋人正式情书版式、信纸视觉、导出备份、升级当轮的一句提示语（「有封信放在桌上了」）

**验证方式**
单测覆盖公式与门槛（含边界：刚好差 1 点、同日多条、跨阶段回填）→ 拿真实历史库跑一次回填，对照条数与天数 → 手动触发一次升级，看信是否生成、是否落到面板。
